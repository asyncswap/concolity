# Uniswap v4-core: what the test suite reaches, and what a planted bug survives

concolity on [Uniswap/v4-core](https://github.com/Uniswap/v4-core) at d153b048 (2026-10-31), forge 1.8.6, solc 0.8.26
with the project's own settings (`via_ir`, `optimizer_runs = 44444444`): the bytecode that ships.

**Scope.** Research on our own tooling, shared as a courtesy. Everything here ran on this machine against the
repository's own test suite, in a local revm: no RPC, no fork, nothing on mainnet or any network. Nothing in this
report is an exploit; where a line rises to a finding it is a gap in what the tests check, listed in §4 for the team.

Three questions, one section each:

1. **Coverage.** Which lines and branch sides of the protocol the 598 tests run, on the shipped bytecode.
2. **Reach.** For a guard no test fires, can any test's input fire it? (`explore`, z3.)
3. **Mutants.** Plant a one-operator bug on a line the fuzz tests run: does any test notice, in forge and in
   concolity, with the same seconds per test? The survivors are the lines no test checks.

```sh
concolity coverage .                                   # 598/598 pass; 12 s with the compile cached
concolity coverage . --at src/libraries/Pool.sol:167   # one line's sides, instant
concolity explore . --target src/libraries/Pool.sol:167 --timeout-ms 3000
concolity bench . --mutate … --tests … --per-test 2 --tools forge,concolity
```

## 1. Coverage

| | Lines | JUMPI sides |
|---|---|---|
| Everything under `src/` (harnesses in `src/test/` included) | 1126/1215 = 92.7% | 1558/2676 = 58.2% |
| **The protocol** (`src/` without `src/test/`) | **611/636 = 96.1%** | **1202/2038 = 59.0%** |

Lines are forge's measure. Sides are both directions of every `JUMPI` in the bytecode, solc's own checks
included, which forge's branch count doesn't see. In the protocol's code, 436 JUMPIs have one side no test takes, and
200 are never reached at all.

The suite agrees with forge on every verdict but one: `TickMathTestTest::test_fuzz_getTickAtSqrtPrice_getSqrtPriceAtTick_relation`
fails in forge with its fixed seed (`0x4444`, 1,000 runs) on an edge tick that 32 random runs don't draw. A
fuzz-input difference, not a runner one (`--against-forge`).

## 2. Reach: can any test fire the tick liquidity cap?

`explore --target src/libraries/Pool.sol:167` takes every fuzz test that reaches the line as a harness and asks z3 for
inputs that take the overflow side. 545 runs, 631 solver calls, 75 s:

| Side | Outcome | Meaning |
|---|---|---|
| `PoolManager` pc 7455, jump | unsat under pinned values, from `StateLibraryTest::test_fuzz_getLiquidity` | the harness's path fixed the storage it reads (the tick's current liquidity), so this says "not from this state", not "never" |
| `PoolTest`'s copy | inputs don't decide the branch | the test runs the line, but `liquidityGrossAfterLower` comes from state built up by earlier calls, not from the call's arguments |

So no single call's arguments can overflow a tick's liquidity: the guard protects against liquidity *accumulated*
across positions, and only a sequence of `modifyLiquidity` calls on one tick could test it. That's a property for an
invariant campaign, which concolity doesn't run yet (it's step 1 of `docs/FUZZ.md`); the suite's own invariant tests
(`test/forge/invariant/`) are where it would live.

### The three mutants no fuzz test killed

- **`Pool.sol:196`, `if (liquidityDelta < 0)` → `<=`: an equivalent mutant, not a gap.** The branch clears a tick
  whose liquidity flipped to zero. With `liquidityDelta == 0`, `liquidityGross` is unchanged, so
  `state.flippedLower` and `flippedUpper` are false (`Pool.sol:531`: `flipped = (after == 0) != (before == 0)`), and
  the body does nothing. No test can tell the two apart because the contracts can't. It survives every test of the
  eight files, and would survive any.
- **`SqrtPriceMath.sol:43`, `if (product / amount == sqrtPX96)` → `!=`: covered, by two hand-picked cases only.**
  This is the overflow check of `amount * sqrtPX96` in `getNextSqrtPriceFromAmount0RoundingUp`. Flipped, the
  non-overflowing case takes the fallback (`mulDivRoundingUp(numerator1, sqrtPX96, …)` through the other formula), which
  gives the same price except at rounding boundaries, so 2 seconds of fuzzing in either tool noticed nothing. Two unit
  tests pin the exact edge (`returnsTheMinimumPriceForMaxInputs`, `sqrtPTimessqrtQOverflows`) and kill it. Fine as it
  is; a fuzz test comparing the fast path against the fallback would make it robust to the next refactor.
- **`TickMath.sol:83`, the `0x4` bit's multiplier `*` → `/`: covered by unit tests, missed by the fuzz tests at
  2 s.** `getSqrtPriceAtTick` multiplies one constant per set bit of the tick. The neighbouring bits (`0x40`, `0x400`,
  `0x4000`, `0x40000`) were killed by `PoolTest`'s fuzz tests in under 5 seconds; bit `0x4` wasn't drawn with a failing
  assertion in time, and three unit tests at fixed ticks catch it. The relation fuzz test that would catch every bit
  is the one that fails on the original (§4.1).

### Rerun, the same evening: the campaign that fuzzes first

The benchmark again after `explore` learned to fuzz before it solves (concolity af5bbe8: mutations over the decoded
arguments with the bytecode's constants as a dictionary, the JUMPI sides as feedback, two symbolic runs at each
plateau, then fuzzing again). `bench` draws its 12 from the 97 sites by position, and the mutation table grew with
the new operators, so this is a **different spread**: `Pool.sol:328` (`sqrtPriceLimitX96 <= MIN_SQRT_PRICE`),
`Pool.sol:503` (`feeGrowthOutside1X128` subtraction), `SqrtPriceMath.sol:43` (`product / amount`),
`SwapMath.sol:61` (`exactIn = amountRemaining < 0`), the `!=` of TickMath's bit tests at 83 and 87, and the same
`Pool.sol:95`, `:196`, `TickMath.sol:91`, `:95`, `:99`, `:139`. Three tools this time: forge, concolity's campaign,
and concolity drawing fresh random inputs with no solver at all. Raw: `bench-2026-10-31-fuzz-first.json`. Run twice
(the first with the solver taking the whole plateau, the second with the two-run turn): identical verdicts.

What the rerun says:

- **Five mutants survive every tool, and four of them are new gaps in the fuzz suite worth a look** (the fifth is
  the equivalent `Pool.sol:196`). `Pool.sol:328` (`<=` → `<`): a swap whose price limit is exactly `MIN_SQRT_PRICE`
  should revert with `PriceLimitOutOfBounds` and instead proceeds; no fuzz test draws the exact limit. `Pool.sol:503`
  (`-` → `+` on the token1 line of `getFeeGrowthInside` when the current tick is at or above the range): fee growth
  inside becomes a sum; the fuzz tests never put a position's range below the current tick with non-zero token1 fee
  growth on both ticks.
  `SqrtPriceMath.sol:43` (`/` → `*`): the overflow check becomes `product * amount == sqrtPX96`, almost always false,
  so every call takes the fallback formula, which agrees except at rounding boundaries, the same reason the `==` flip
  survived in the morning run. `SwapMath.sol:61` (`exactIn = amountRemaining < 0` → `<=`): a zero `amountRemaining` is
  exact-output in the shipped code and exact-input in the mutant; no fuzz test draws a zero amount, so whether the
  two paths agree there is untested. These belong with §4.3 as
  observations for the team: none is exploitable (each is a planted bug the shipped code does not have), each marks
  an input the fuzz tests do not draw.
- **Coverage, measured on the shipped bytecode across the five files (634 sides): the campaign took 182 sides, forge's
  corpus 175 (194 inputs), 173 in common.** The campaign reaches 9 sides forge's corpus does not, on `Pool.sol` and
  `TickBitmap.sol`; the morning's figure was 111 against 162. Coverage is the solver's contribution, and it holds.
- **Kills are not: the campaign killed 4 where fresh random inputs killed 6 and forge 7, and the shorter solver turn
  did not move it.** The two the campaign misses and random gets (`TickMath.sol:83`, `:91`) fall to random in 0.2 s and
  2.3 s, so the campaign's fuzz phase is not doing what random does: it mutates the handful of seeds it has, one leaf
  at a time, and a bit flip or a dictionary word on a tick argument rarely lands on the ticks these multipliers
  change. Fresh draws spread over the whole `int24` range do. That is the next change in `explore`, not more solver
  tuning: mix fresh random inputs into the fuzz phase (one in four runs), and treat a kill by either as a kill.
- forge's one unique kill, `TickMath.sol:95`, came at 2.7 s of its 2-second budget on a test it reached late; a
  longer run gets it in random too (the morning's run killed the neighbouring bits the same way).

## 4. For the team

Low or informational, all about the test suite; nothing here is an exploit. In order of what I'd fix first.

### 4.1 `test_fuzz_getTickAtSqrtPrice_getSqrtPriceAtTick_relation` fails on a valid input (low)

`test/libraries/TickMath.t.sol:205`. The test bounds `tick` to `[MIN_TICK, MAX_TICK - 1]` and checks, last,
`getTickAtSqrtPrice(getSqrtPriceAtTick(tick + 1)) == tick + 1`. For `tick = MAX_TICK - 1`, `tick + 1` is `MAX_TICK`,
whose price is `MAX_SQRT_PRICE`, and `getTickAtSqrtPrice` rejects it by design (`InvalidSqrtPrice`: the valid range is
`[MIN_SQRT_PRICE, MAX_SQRT_PRICE)`). forge 1.8.6 reaches it from the fuzzer's out-of-range draw `-887273`, which
forge-std's `bound` wraps to `887271 = MAX_TICK - 1`:

```
[FAIL: InvalidSqrtPrice(1461446703485210103287273052203988822378723970342)]
  counterexample: args=[-887273]   (profile default: runs = 1000, seed = 0x4444)
```

CI pins forge v1.3.6 (`.github/workflows/tests-*.yml`), whose fuzzer with the same seed doesn't draw that edge, so the
suite is green there and red on a current forge. Fix: bound to `MAX_TICK - 2`, or skip the last assertion when
`nextTick == MAX_TICK`. Until then this test can't judge the `TickMath` mutants (it would catch every bit's
multiplier in one run).

A drop-in test for `test/libraries/` exists and is kept locally, unpublished: the edge as the existing test asks for
it (and the `InvalidSqrtPrice` it gets), the fuzzer's draw that reaches it (`bound(-887273, …)` is `MAX_TICK - 1`),
the relation bounded to `MAX_TICK - 2`, and the top tick checked on its own. 4 tests, 2,000 runs, all pass on
d153b048. This write-up is the proof of concept; reproduce with
`forge test --match-test test_fuzz_getTickAtSqrtPrice_getSqrtPriceAtTick_relation` on forge 1.8.6.

### 4.2 Guard reverts never exercised from `PoolManager`'s own bytecode (informational)

From §1: `ManagerLocked` (`PoolManager.sol:97`), `CurrencyNotSettled` (112), `HookAddressNotValid` (126),
`TicksMisordered`, `TickLowerOutOfBounds`, `TickUpperOutOfBounds` (`Pool.sol:95–97`), `TickLiquidityOverflow`
(`Pool.sol:167/170`). Some are tested through harness copies of the library (`PoolTest`); `TickLowerOutOfBounds` isn't
tested in either copy. A test per revert, through the manager, is cheap; the mutant run shows the fuzz tests do reach
`tickLower == tickUpper` (`Pool.sol:95` was killed in 0.2 s), so the gap is the assertion, not the reach.

### 4.3 `Pool`'s fee setters and the tick liquidity cap run from no protocol path in the suite (informational)

`Pool.sol:106, 109, 115, 117` (`setProtocolFee`, `setLPFee`, the initialize write of `lpFee`) and `ProtocolFees.sol:39`
never run from the protocol's bytecode; `Pool.sol:168/171` (`TickLiquidityOverflow`) never revert. §2 shows the cap
can't be reached by any single call's arguments: it needs liquidity accumulated on one tick across positions, i.e. an
invariant test that keeps adding to one tick until the cap, or a unit test that sets up a tick at the cap.

### 4.4 The FullMath invariant fuzz tests reject most inputs (informational)

`test_invariant_mulDiv` and `test_invariant_mulDivRoundingUp` guard with `vm.assume(!resultOverflows(x, y, d))`, which
rejects most random triples. At the configured 1,000 runs they stay under forge's 65,536-rejection cap; a longer
campaign (the `ci` profile's 100,000 runs multiplies rejections too) or any time-boxed run trips "vm.assume rejected too
many inputs". Drawing `x` and `y` so that the product fits (`bound` on one of them from the other) would make the tests
run their full budget on accepted inputs.
